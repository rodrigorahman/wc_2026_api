## 2. Objetivo da Task
Estender `config.Config` com `ResendAPIKey` e `ResendFromEmail`, carregados via viper (`AutomaticEnv`) em `Load()`, com **fail-fast condicional** espelhando `JWT_SECRET`: em produção (`!IsDevelopment`) a ausência de `RESEND_API_KEY` aborta o boot; em dev a ausência é permitida (o wiring escolherá `NoopSender`). Quando a key está presente, `RESEND_FROM_EMAIL` torna-se obrigatório (sem remetente não há envio). Segredo nunca logado.

---

## 3. Descrição Detalhada

### `internal/infra/config/config.go`
- `Config`: adicionar `ResendAPIKey string` e `ResendFromEmail string`.
- Em `Load()`, após carregar e validar `JWT_SECRET`:
  - Ler `RESEND_API_KEY` e `RESEND_FROM_EMAIL` via viper.
  - Determinar o ambiente com a lógica existente (`Env` → `IsDevelopment()` via aliases `dev`/`development`).
  - **Política condicional**:
    - Não-dev **e** `RESEND_API_KEY` vazio → `error` referenciando `RESEND_API_KEY` (espelha a mensagem do `JWT_SECRET`).
    - `RESEND_API_KEY` presente (qualquer ambiente) **e** `RESEND_FROM_EMAIL` vazio → `error` referenciando `RESEND_FROM_EMAIL`.
    - Dev sem key → `Config` válida com ambos os campos vazios.
  - Atribuir os valores aos campos de `Config`.
- Manter o estilo de erro fail-fast existente (retorna `error`, nunca `os.Exit`/`log.Fatal`). Segredo **nunca** entra na mensagem de erro nem em log.

> **Fora de escopo**: o consumo da config para escolher `Resend`/`Noop` (T9).

## 7. Notas / Observações
- A política condicional do `RESEND_FROM_EMAIL` (exigido sempre que a key está presente, inclusive em dev) é a interpretação **conservadora** adotada — sem remetente, o `ResendSender` não consegue enviar. Coerente com tech_spec §11.6.
- `viper.New()` é instanciado dentro de `Load()` (padrão existente) — `t.Setenv` basta para isolar; sem `viper.Reset`.
- Atenção à regressão: os testes existentes de `Load` que não setam `APP_ENV` assumem default `production` — podem passar a exigir `RESEND_API_KEY`. Ajustar conforme a recomendação do QA.
