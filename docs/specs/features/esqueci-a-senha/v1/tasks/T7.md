## 2. Objetivo da Task
Implementar `AuthService.ChangePassword`: valida estritamente a senha temporária (correta **e** não expirada), grava a nova senha via `UpdatePassword` (que zera as colunas temp na mesma operação) e dispara o e-mail de notificação de troca (best-effort). A troca só funciona pós-recuperação; nunca aceita a senha vigente.

---

## 3. Descrição Detalhada

### `ChangePassword(ctx, userID, tempPassword, newPassword string) error` (em `auth_service.go`)
O `userID` vem do `sub` do token, repassado pelo handler (T8) — nunca de input do cliente (anti-IDOR).
1. `GetUserByID(userID)`. `ErrUserNotFound` ou outro erro → `codes.Internal` (`"erro interno"`).
2. **Validação estrita da temporária** — falha em qualquer condição retorna `codes.InvalidArgument` (`"senha temporária inválida ou expirada"`):
   - `user.TempPasswordHash != ""` (há temp ativa);
   - `s.clk.Now().Before(user.TempPasswordExpiresAt)` (não expirada — mesma fronteira `Before` do Login);
   - `s.compareHash([]byte(user.TempPasswordHash), []byte(tempPassword)) == nil` (temp correta).
3. `bcrypt.GenerateFromPassword(newPassword, s.bcryptCost)` → hash; erro → `codes.Internal`.
4. `UpdatePassword(userID, string(hash))` — zera `temp_password_hash`/`temp_password_expires_at` no mesmo UPDATE (RN8). Erro → `codes.Internal`.
5. **Notificação best-effort**: `EmailSender.Send(ctx, user.Email, assunto, corpo)` — corpo pt-BR informando alteração e orientando redefinição se não reconhecida; **nunca** contém senha/temp (RN11/CA-09). Falha de envio → log (`to`/`subject`/`err`) e a troca permanece efetivada (CA-12); `ChangePassword` retorna `nil`.

> A ordem importa: `UpdatePassword` **antes** do `Send`. Assim a troca é efetivada independentemente do e-mail (CA-12).

> **Fora de escopo**: handler/proto (T8). Aqui só o método de service.

## 4. Aceite Técnico (critérios objetivos)
A task estará concluída quando:
- [ ] Temp correta e não expirada → `UpdatePassword` com hash bcrypt da nova senha; campos temp zerados.
- [ ] Temp incorreta / expirada / ausente → `InvalidArgument`; `UpdatePassword` **não** chamado.
- [ ] E-mail de notificação enviado após troca bem-sucedida; body sem senha (CA-11).
- [ ] Falha no e-mail de notificação → troca efetivada, retorna `nil` (CA-12).
- [ ] `userID` usado é o do `sub` (validado no handler T8) — assinatura recebe `userID`, nunca lê de input.
- [ ] `make test` verde para o pacote service.

## 7. Notas / Observações
- Validação **estrita** contra a temporária é decisão do dono do produto (tech_spec §21): `ChangePassword` não aceita a senha vigente — só funciona pós-recuperação.
- O envio da notificação é best-effort; deve permanecer **observável e determinístico** no teste (mock de `EmailSender`). Se o executor optar por dispatch assíncrono (como em `RequestPasswordRecovery`), garantir sincronização no teste; o caminho mais simples e testável é envio síncrono best-effort após `UpdatePassword` (não há requisito de latência/anti-enumeração aqui, diferente do pedido de recuperação).
- Mesma fronteira de expiração `Before` do Login (T6) — consistência.
