## 2. Objetivo da Task
Cobrir o fluxo de recuperação ponta-a-ponta pela cadeia real de interceptors: estender `TestNewBufconnServer` para injetar um `EmailSender` fake e uma geração de senha temporária determinística, e escrever os testes E2E (CT-028..CT-034) — incluindo o fluxo completo recovery → login(temp) → change → login(nova) → login(temp) negado.

## 3. Descrição Detalhada

### `internal/testutil/bufconn.go` — injeção de seams de teste
- Estender `TestNewBufconnServer` (ou adicionar variante) para aceitar, opcionalmente, um `EmailSender` fake — via `fx.Decorate`/`fx.Replace` sobre o bind de `service.EmailSender` (mesmo mecanismo já usado para `clock.Clock`).
- Tornar a senha temporária **determinística** no servidor de teste: injetar o `genTempPassword` de teste. Coordene com T5/T9 o seam fx para o `genTempPassword` (ex.: provider opcional que o bufconn sobrescreve). Se um seam fx limpo não for viável sem alargar T5/T9, a alternativa aceita (tech_spec §19) é o teste chamar `processRecovery` diretamente no setup; nesse caso, **registrar** a limitação de sincronização da goroutine em "cenários não cobertos".
- O fake `EmailSender` captura `to`/`subject`/`body` e nunca falha (NoopSender-like), permitindo asserções e sincronização.

### `test/e2e/auth_e2e_test.go` — fluxos
Implementar CT-028..CT-034 (detalhes na seção 6.3). O fluxo completo (CT-032) é o de maior valor: depende do `genTempPassword` determinístico (ou do `processRecovery` direto) para conhecer a senha temporária sem revertê-la do banco.

> **Fora de escopo**: lógica de produção (service/handler/module/server) — tudo em T5..T9. Aqui só helper de teste + testes E2E.

### 6.3 Testes E2E

#### Fluxo: Resposta genérica independente de existência (CT-028)
- **CA**: CA-01, CA-02
- **Objetivo**: confirmar anti-enumeração por resposta ponta-a-ponta (cadeia real de interceptors).
- **Pré-condições**: `TestNewBufconnServer`; um usuário registrado; um e-mail desconhecido.
- **Passos**: registrar usuário → `RequestPasswordRecovery(email do usuário)` → `RequestPasswordRecovery(email desconhecido)` → comparar mensagens e status.
- **Validações**: mensagens idênticas; ambos `OK`. (table-driven, 2 sub-casos)

#### Fluxo: RequestPasswordRecovery sem token é público (CT-029)
- **CA**: —
- **Objetivo**: garantir que o RPC não é bloqueado pelo interceptor JWT (public method configurado em T9).
- **Pré-condições**: `TestNewBufconnServer`.
- **Passos**: chamar `RequestPasswordRecovery` sem metadata de auth.
- **Validações**: `status.Code != Unauthenticated`; resposta `OK`.

#### Fluxo: ChangePassword sem token é bloqueado (CT-030)
- **CA**: —
- **Objetivo**: garantir proteção JWT antes do handler.
- **Pré-condições**: `TestNewBufconnServer`.
- **Passos**: chamar `ChangePassword` sem `Authorization`.
- **Validações**: `codes.Unauthenticated` (simetria com `GetMe`).

#### Fluxo: ChangePassword com token válido e temp errada (CT-031)
- **CA**: CA-06
- **Objetivo**: demonstrar que o handler é alcançado com token válido e o service rejeita temp incorreta.
- **Pré-condições**: usuário com temp ativa; login com temp para obter token; clock fixo.
- **Passos**: setup temp → login(temp) → `ChangePassword(authCtx, {temp errada, nova})`.
- **Validações**: `codes.InvalidArgument`.

#### Fluxo: Recovery completo (CT-032) — MAIOR VALOR
- **CA**: CA-04, CA-06, CA-07
- **Objetivo**: validar o ciclo inteiro ponta-a-ponta.
- **Pré-condições**: `TestNewBufconnServer` com clock fixo + `EmailSender` fake + temp determinística.
- **Passos**: Register → RequestPasswordRecovery → (obter temp determinística) → Login(temp) [`PasswordChangeRequired==true`] → ChangePassword(temp, nova) [`OK`] → Login(nova) [`OK`, `false`] → Login(temp antiga) [`Unauthenticated`].
- **Validações**: todos os CAs 04/06/07 ponta-a-ponta.

#### Fluxo: Login com senha original durante recovery ativa (CT-033)
- **CA**: CA-10
- **Objetivo**: confirmar `PasswordChangeRequired=false` no proto response com original + temp ativa.
- **Pré-condições**: usuário com original + temp ativa; clock fixo.
- **Passos**: setup temp → Login(original).
- **Validações**: `PasswordChangeRequired == false`; `AccessToken` não vazio.

#### Fluxo: Login com temp válida (CT-034)
- **CA**: CA-04
- **Objetivo**: confirmar `PasswordChangeRequired=true` mapeado no proto response.
- **Pré-condições**: usuário com temp ativa não expirada; clock fixo.
- **Passos**: Login(temp).
- **Validações**: `PasswordChangeRequired == true`. (companion de CT-033)
